[[oid4vp-deployment-configuration]]
== OpenID4VP deployment configuration reference

The following `oid4vp-authenticator` settings control how the verifier builds
OpenID4VP authorization requests and validates responses.

=== Core settings

[cols="1,1,2"]
|===
|Setting |Example |Purpose

|`clientIdentifierPrefix`
|`x509_hash`
a|How `client_id` is built in authorization requests.
The OpenID4VP client identifier prefixes recognized in this plugin's model are:
`redirect_uri`, `openid_federation`, `decentralized_identifier`, `verifier_attestation`, `x509_san_dns`, `x509_hash`, and `origin`.
Only `x509_san_dns` (default in the authenticator UI) and `x509_hash` are implemented for building `client_id` here:
`x509_san_dns` uses the Keycloak frontend hostname; `x509_hash` uses a hash derived from the configured `accessCertificate`.

|`queryLanguage`
|`dcql_query`
|Which credential query shape is placed in the signed request object: `dcql_query`, `dif_presentation_exchange`, or `all` (both).

|`responseMode`
|`direct_post.jwt`
a|How the wallet delivers the authorization response to the verifier `response_uri`.
The plugin's `ResponseMode` model includes `fragment`, `form_post`, `direct_post`, `direct_post.jwt`, and `query`.
The `oid4vp-authenticator` configuration UI only offers `direct_post` (default) and `direct_post.jwt`.
Use `direct_post` for a conventional form post (`vp_token`, `state`, and related fields).
Use `direct_post.jwt` when the wallet must post a single encrypted JWE in the `response` form field; the verifier then advertises an ephemeral encryption key via `client_metadata.jwks`.

|`requestUriMethod`
|`get`
a|How wallets should dereference `request_uri`.
Supported values: `get` (default) and `post`.
When set to `post`, the wallet sends an HTTP POST to the request URI with `wallet_nonce` and optional `wallet_metadata` form parameters.

|`customUrlScheme`
|`openid4vp://`
|Wallet invocation URL scheme embedded in authorization request links.

|`accessCertificate`
|`MIIC...`
|Base64 DER X.509 certificate (or PEM body without `-----BEGIN/END CERTIFICATE-----` delimiters) injected into request object `x5c` header.

|`registrationCertificate`
|`eyJ...`
|Opaque registration certificate value exposed via `verifier_info`.
|===

=== Supported credential formats

The plugin supports two credential formats:

* https://www.ietf.org/archive/id/draft-ietf-oauth-sd-jwt-vc-13.html[SD-JWT VC] (`dc+sd-jwt`): The default format. Verifiable credentials using Selective Disclosure JSON Web Tokens.
* https://www.iso.org/standard/69084.html[mDL/mdoc] (`mso_mdoc`): ISO/IEC 18013-5 mobile documents. Used primarily for government-issued credentials such as the German wallet PID.

Both formats can be used individually or combined in a single authentication profile.
For mDoc credentials, claims must be specified using the `namespace/elementIdentifier` notation (for example `eu.europa.ec.eudi.pid.1/given_name`).

=== Authentication profile settings

[cols="1,1,2"]
|===
|Setting |Example |Purpose

|`profiles`
|`(JSON array)`
|JSON array of authentication profiles that define which credentials are requested and how they are verified.
When empty, a legacy single-credential profile is generated from `credentialTypes`.
See <<_authentication_profiles>> below for the full format.

|`credentialTypes`
|`https://credentials.example.com/identity_credential`
|Comma-separated list of credential types accepted by the authenticator.
Only applies when no authentication profile is configured.
Interpreted per credential format (for example `vct` for SD-JWT VC, `docType` for mDoc).
|===

=== Authentication profiles

Authentication profiles define which credentials are requested during the OpenID4VP flow and how they are verified.
Each profile specifies one or more credential requirements and how they relate to each other.

==== Profile structure

[source,json]
----
[
  {
    "id": "my-profile",
    "description": "A descriptive label",
    "displayCta": { "en": "Sign in with wallet" },
    "enabledForClients": ["optional-client-filter"],
    "credentials": [ ... ],
    "credentialGroups": [ ... ]
  }
]
----

[cols="1,3"]
|===
|Field |Description

|`id`
|Unique identifier for the profile. Required.

|`description`
|Human-readable description of the profile.

|`displayCta`
|Map of locale to button text shown on the login page. Defaults to "Sign in with a wallet".

|`enabledForClients`
|Optional list of client IDs for which this profile is available. When empty or omitted, the profile is available to all clients.

|`credentials`
|Array of credential requirement objects. At least one is required.

|`credentialGroups`
|Optional array of credential group objects for alternative credential selection.
|===

==== Credential requirements

Each credential requirement object defines a single credential to be requested:

[source,json]
----
{
  "id": "identity",
  "role": "primary",
  "format": "dc+sd-jwt",
  "credentialTypes": ["https://credentials.example.com/identity_credential"],
  "claims": ["sub"],
  "trust": [{ "type": "self" }],
  "binding": [],
  "identitySource": "credential"
}
----

[cols="1,1,3"]
|===
|Field |Default |Description

|`id`
|Required
|Unique identifier for this credential within the profile.

|`role`
|`supporting`
|Either `primary` or `supporting`. The primary credential determines the authenticated user.

|`identitySource`
|`credential`
|Either `credential` (login) or `session` (presentation during issuance). See <<presentation-during-issuance>>.

|`format`
|`dc+sd-jwt`
|Credential format: `dc+sd-jwt` for SD-JWT VC or `mso_mdoc` for mDoc.

|`credentialTypes`
|Required
|Credential types to request. For SD-JWT VC, these are `vct` values. For mDoc, exactly one `docType` is required.

|`claims`
|Required
|Claims to request. For mDoc, use `namespace/elementIdentifier` notation.

|`trust`
|`[{ "type": "self" }]`
|Trust policies for verifying the credential issuer.

|`binding`
|`[]`
|Binding rules for supporting credentials.

|===

[NOTE]
====
A profile must have exactly one primary credential, except when `credentialGroups` are used to select between alternative primary credentials.
The primary credential must request the configured `subjectClaim`—`sub` by default (unless `identitySource` is `session`).
====

==== Trust policies

Trust policies define how the issuer of a credential is verified.

.Self-trust (`self`)
[source,json]
----
{ "type": "self" }
----

Used for credentials issued by the same Keycloak instance. Not supported for mDoc credentials.

.X.509 certificate trust (`x5c`)
[source,json]
----
{
  "type": "x5c",
  "anchors": ["<base64-encoded-x509-certificate>"]
}
----

Validates the credential issuer against one or more X.509 trust anchors. The anchor is the Base64-encoded DER certificate.

.EUDI PID trust list (`eudi_pid_trust_list`)
[source,json]
----
{
  "type": "eudi_pid_trust_list",
  "trustListUrl": "https://example.com/trust-list.jwt",
  "trustListSigningCertificate": "<base64-DER-certificate>",
  "serviceType": "http://uri.etsi.org/19602/SvcType/PID/Issuance"
}
----

Validates the credential issuer against a EUDI trust list. The `trustListSigningCertificate` anchors the trust-list JWT signature, and `serviceType` filters entries by service type.

==== Binding rules

Binding rules ensure that supporting credentials are bound to the primary credential or the authenticated user.
They are configured on supporting credentials only.

.Claim equals primary claim
[source,json]
----
{
  "type": "claim_equals_primary_claim",
  "credentialClaim": "username",
  "primaryCredentialClaim": "username"
}
----

Verifies that a claim in the supporting credential matches a claim in the primary credential.

.Claim equals user attribute
[source,json]
----
{
  "type": "claim_equals_user_attribute",
  "credentialClaim": "family_name",
  "userAttribute": "lastName"
}
----

Verifies that a claim in the supporting credential matches a Keycloak user attribute. Built-in attribute mappings: `given_name`/`firstName`, `family_name`/`lastName`, `username`/`preferred_username`. Any other value is looked up as a custom user attribute.

==== Credential groups

Credential groups allow the wallet to choose between alternative credential combinations.
This is useful when multiple credential types can satisfy the same authentication requirement.

[source,json]
----
{
  "id": "primary-identity",
  "required": true,
  "options": [
    ["national-id"],
    ["drivers-license"]
  ]
}
----

[cols="1,3"]
|===
|Field |Description

|`id`
|Unique identifier for the group.

|`required`
|Whether the group is required (default: `true`).

|`options`
|Array of alternative credential combinations. Each option is an array of credential IDs that must all be presented together.
|===

When credential groups are used, the profile may contain multiple primary credentials.
Exactly one credential group must select a primary credential, and that group must be required.

[[presentation-during-issuance]]
==== Presentation during issuance

Presentation during issuance allows Keycloak to request a credential presentation as part of an OID4VCI issuance flow.
In this mode, the user identity comes from the issuance session rather than from claims in the presented credential.

To configure a presentation-during-issuance profile, set `identitySource` to `session` on the primary credential.
Binding rules are mandatory for session-identity credentials so that the presented credential is verified against the authenticated user.

[source,json]
----
{
  "id": "issuance-step",
  "displayCta": { "en": "Presentation during issuance" },
  "enabledForClients": ["test-app"],
  "credentials": [
    {
      "id": "pid",
      "role": "primary",
      "identitySource": "session",
      "format": "mso_mdoc",
      "credentialTypes": ["eu.europa.ec.eudi.pid.1"],
      "claims": ["eu.europa.ec.eudi.pid.1/given_name", "eu.europa.ec.eudi.pid.1/family_name"],
      "binding": [
        {
          "type": "claim_equals_user_attribute",
          "credentialClaim": "eu.europa.ec.eudi.pid.1/family_name",
          "userAttribute": "lastName"
        }
      ]
    }
  ]
}
----

Session-identity profiles are hidden from the login page and are only activated through internal OID4VCI flows.

=== Request and response settings

[cols="1,1,2"]
|===
|Setting |Example |Purpose

|`transactionData`
|`(base64url-encoded JSON)`
|Optional comma-separated or newline-separated base64url-encoded `transaction_data` JSON objects (OpenID4VP Final section 5.1).
Requires holder binding.
Entries are normalized before signing; use the signed request JWT payload as the canonical wire form when debugging hash mismatches.
Only `sha-256` is supported for `transaction_data_hashes`.

|`verifierInfo`
|`(JSON array)`
|Optional JSON array of `verifier_info` objects (`{format, data, credential_ids?}`) merged with the registration certificate entry.
|===

=== Holder binding settings

[cols="1,1,2"]
|===
|Setting |Default |Purpose

|`requireCryptographicHolderBinding`
|`true`
|When true, the DCQL query requests a presentation with a Key Binding JWT.
When false, the request omits the KB-JWT requirement and state binding is enforced on the response (OpenID4VP Final section 5.3).

|`holderBindingProofMaxAge`
|`60`
|Maximum age in seconds of accepted holder-binding proofs (for example KB-JWT for SD-JWT VC).
Used as a replay protection measure.
Currently only applies to SD-JWT VC; mDoc does not specify a device-signed timestamp that would allow a holder-binding age check.
|===

=== Verification policy settings

[cols="1,1,2"]
|===
|Setting |Default |Purpose

|`requireNbfClaim`
|`false`
|Require the `nbf` (Not Before) time claim to be present in presented SD-JWT VC credentials.

|`requireExpClaim`
|`false`
|Require the `exp` (Expiration) time claim to be present in presented SD-JWT VC credentials.

|`verifyIssuerClaim`
|`true`
|Require the `iss` claim in presented SD-JWT VC credentials to match this realm's issuer URL.

|`fallbackToIsoSpecSessionTranscript`
|`false`
|Allow falling back to the ISO-spec session transcript algorithm when verification with the OpenID4VP-spec session transcript algorithm fails (mDoc only).

|`enforceRevocationStatus`
|`false`
|Reject credentials whose status indicates they are no longer valid, as per the Token Status List mechanism.
|===

[source,json]
----

  "config": {
    "clientIdentifierPrefix": "x509_hash",
    "queryLanguage": "dcql_query",
    "responseMode": "direct_post.jwt",

    "accessCertificate": "<base64-der-x509-cert>",

----

If you provision Keycloak using Terraform or similar tooling, map these settings to your own
module/input variable names according to your deployment conventions.

=== Configuring primary credential identity claims

When the primary credential is used to identify the Keycloak user, `subjectClaim` controls which claim is used for user resolution.

`subjectClaim`::
  The claim used to resolve the Keycloak user by *user id*.
  Defaults to `sub`.

For mDoc credentials, claims are namespaced using the `namespace/element` format defined by ISO 18013-5.
For example, a PID mDoc identifies a person by:

[source,text]
----
namespace: eu.europa.ec.eudi.pid.1
element:   given_name
Namespaced form: eu.europa.ec.eudi.pid.1/given_name
----

When configuring a primary mDoc credential for authentication, set `subjectClaim` to a namespaced claim that uniquely identifies the user (e.g. `eu.europa.ec.eudi.pid.1/personal_administrative_number`).
Do *not* set `subjectClaim` to a bare element like `document_number` unless it is globally unique across issuers.

The following example shows the identity claim configuration for a primary mDoc credential.
The `trust` configuration is omitted for brevity — refer to the trust configuration sections above.

[source,json]
----
{
  "id": "main",
  "role": "primary",
  "format": "mso_mdoc",
  "credentialTypes": [
    "eu.europa.ec.eudi.pid.1"
  ],
  "subjectClaim": "eu.europa.ec.eudi.pid.1/personal_administrative_number",
  "claims": [
    "eu.europa.ec.eudi.pid.1/personal_administrative_number",
    "eu.europa.ec.eudi.pid.1/given_name",
    "eu.europa.ec.eudi.pid.1/family_name"
  ],
  "trust": [ ... ]
}
----

For SD-JWT VC credentials, use standard claim names such as `sub` — no namespace is needed.

==== Access certificate guidance for sandbox onboarding

To register a verifier in the SPRIN-D sandbox, it is recommended to bind `accessCertificate`
to an ES256 signing key in the realm and to a DNS name representing your deployment.

- *Key algorithm*: use an EC P-256 (ES256) realm key for request-object signatures.
- *DNS value*: use the public hostname of your deployment (for example
  `keycloak-demo.solutions.adorsys.com`), and ensure it is the DNS value represented in the certificate.
- *Public key sharing*: when sandbox onboarding asks for a public key, provide the PEM-encoded
  public key corresponding to the same ES256 key/certificate pair.

A typical workflow is:

. Select or generate an ES256 key provider in the realm.
. Issue/provide an X.509 certificate for that key, with SAN DNS matching your deployment hostname.
. Set `accessCertificate` to that certificate content (base64 DER, or PEM body without delimiters).
. If required by the sandbox portal, extract and submit the corresponding public key in PEM form.
