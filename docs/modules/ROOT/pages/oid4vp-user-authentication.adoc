[[oid4vp-authentication]]
== Authenticate users with verifiable credentials over OpenID4VP

{project_name} implements support for authenticating users as they present verifiable credentials issued to them by itself.
This is done over https://openid.net/specs/openid-4-verifiable-presentations-1_0.html[OpenID for Verifiable Presentation (OpenID4VP)].
This chapter describes how to interact with this feature.

[IMPORTANT]
====
This feature is experimental. Backward compatibility is not guaranteed, and future updates may introduce breaking changes.
====

=== What is covered in this chapter

- Enabling user authentication over OpenID4VP
- Initiating the flow by retrieving an authentication request
- Polling for the status of the authentication session
- Completing OIDC login with OpenID4VP authentication
- Supported credential formats
- Configuring authentication profiles
- Configuring the verifier policy for OpenID4VP authentication

=== Enabling user authentication over OpenID4VP

To enable user authentication over OpenID4VP, make sure to add the following flags to the startup command:

[source,bash]
----
--features=oid4vc-vci
----

Verify activation by checking the server logs.
The `oid4vc-vci` feature must equally be activated because the feature relies on {project_name} being able to https://www.keycloak.org/docs/latest/server_admin/index.html#_oid4vci[issue verifiable credentials] to users itself.

=== Supported credential formats

The plugin supports two credential formats:

* https://www.ietf.org/archive/id/draft-ietf-oauth-sd-jwt-vc-13.html[SD-JWT VC] (`dc+sd-jwt`): The default format. Verifiable credentials using Selective Disclosure JSON Web Tokens.
* https://www.iso.org/standard/69084.html[mDL/mdoc] (`mso_mdoc`): ISO/IEC 18013-5 mobile documents. Used primarily for government-issued credentials such as the German wallet PID.

Both formats can be used individually or combined in a single authentication profile.
For mDoc credentials, claims must be specified using the `namespace/elementIdentifier` notation (for example `eu.europa.ec.eudi.pid.1/given_name`).

=== Initiating the flow by retrieving an authentication request

To retrieve an authentication request, send a GET request to the `/oid4vp-auth/request` endpoint.
The request must carry a `client_id` query parameter to indicate the client to link with the authentication session.

[source,bash]
----
GET /realms/<realm>/oid4vp-auth/request?client_id=<client_id>
----

==== Optional parameters

[cols="1,1,3"]
|===
|Parameter |Type |Description

|`profile_id`
|String
|Selects which authentication profile to use. When omitted, the default profile is selected.

|`code_challenge`
|String
|PKCE code challenge (S256). Required for API-driven flows that use the `/code` endpoint for authorization code redemption.

|`code_challenge_method`
|String
|Must be `S256` when `code_challenge` is provided.
|===

==== Response

The endpoint returns an object containing:

* an OpenID4VP authorization request link that can be used to initiate the authentication flow, either directly or by generating a QR code from it;
* a transaction ID for inquiring the status of the thereby opened authentication session.

[source,json]
----
{
  "authorization_request": "openid4vp://?client_id=<client_id>&request_uri=<request_uri>",
  "transaction_id": "<transaction_id>"
}
----

=== Polling for the status of the authentication session

Because the OpenID4VP authentication flow is implied to be pursued cross-device, the initiating client needs to asynchronously check the status of the authentication session.
For this, send a GET request to the `/oid4vp-auth/status` endpoint, passing the transaction ID received in the previous step.

[source,bash]
----
GET /realms/<realm>/oid4vp-auth/status/<transaction_id>
----

The response is an object containing the status of the authentication session, which can be one of the following: `pending`, `success`, or `error`.
In case of a successful authentication, the response also contains an *authorization code* to exchange for an access token.
In case of an error, the response contains error details.

.Pending authentication
[source,json]
----
{
  "status": "pending"
}
----

.Successful authentication
[source,json]
----
{
  "status": "success",
  "authorization_code": "<code>"
}
----

.Error during authentication
[source,json]
----
{
  "status": "error",
  "error": "<error_type>",
  "error_description": "<error_description>"
}
----

=== Redeeming an authorization code (API-driven flows)

For API-driven flows that use PKCE, the client must exchange the authorization code obtained from the status endpoint by calling the `/oid4vp-auth/code` endpoint.

[source,bash]
----
POST /realms/<realm>/oid4vp-auth/code
Content-Type: application/x-www-form-urlencoded

transaction_id=<transaction_id>&code_verifier=<code_verifier>
----

The response contains the authorization code that can be exchanged for an access token:

[source,json]
----
{
  "authorization_code": "<code>"
}
----

=== Complete OIDC login with OpenID4VP authentication

The integration of OpenID4VP authentication into the OIDC login flow is readily available provided you enable the `keycloak.v2+oid4vp` login theme that supports the feature.

When multiple authentication profiles are configured, the login page displays a button for each profile.
Profiles marked as session-identity profiles (used for presentation during issuance) are hidden from the login page and are only activated through internal OID4VCI flows.

=== Authentication profiles

Authentication profiles define which credentials are requested during the OpenID4VP flow and how they are verified.
Each profile specifies one or more credential requirements and how they relate to each other.

==== Profile structure

[source,json]
----
[
  {
    "id": "my-profile",
    "description": "A descriptive label",
    "displayCta": { "en": "Sign in with wallet" },
    "enabledForClients": ["optional-client-filter"],
    "credentials": [ ... ],
    "credentialGroups": [ ... ]
  }
]
----

[cols="1,3"]
|===
|Field |Description

|`id`
|Unique identifier for the profile. Required.

|`description`
|Human-readable description of the profile.

|`displayCta`
|Map of locale to button text shown on the login page. Defaults to "Sign in with a wallet".

|`enabledForClients`
|Optional list of client IDs for which this profile is available. When empty or omitted, the profile is available to all clients.

|`credentials`
|Array of credential requirement objects. At least one is required.

|`credentialGroups`
|Optional array of credential group objects for alternative credential selection.
|===

==== Credential requirements

Each credential requirement object defines a single credential to be requested:

[source,json]
----
{
  "id": "identity",
  "role": "primary",
  "format": "dc+sd-jwt",
  "credentialTypes": ["https://credentials.example.com/identity_credential"],
  "claims": ["sub", "username"],
  "trust": [{ "type": "self" }],
  "binding": [],
  "identitySource": "credential"
}
----

[cols="1,1,3"]
|===
|Field |Default |Description

|`id`
|Required
|Unique identifier for this credential within the profile.

|`role`
|`supporting`
|Either `primary` or `supporting`. The primary credential determines the authenticated user.

|`identitySource`
|`credential`
|Either `credential` (login) or `session` (presentation during issuance). See <<presentation-during-issuance>>.

|`format`
|`dc+sd-jwt`
|Credential format: `dc+sd-jwt` for SD-JWT VC or `mso_mdoc` for mDoc.

|`credentialTypes`
|Required
|Credential types to request. For SD-JWT VC, these are `vct` values. For mDoc, exactly one `docType` is required.

|`claims`
|Required
|Claims to request. For mDoc, use `namespace/elementIdentifier` notation.

|`trust`
|`[{ "type": "self" }]`
|Trust policies for verifying the credential issuer.

|`binding`
|`[]`
|Binding rules for supporting credentials.

|===

[NOTE]
====
A profile must have exactly one primary credential, except when `credentialGroups` are used to select between alternative primary credentials.
The primary credential must request `sub` and `username` claims (unless `identitySource` is `session`).
====

==== Trust policies

Trust policies define how the issuer of a credential is verified.

.Self-trust (`self`)
[source,json]
----
{ "type": "self" }
----

Used for credentials issued by the same {project_name} instance. Not supported for mDoc credentials.

.X.509 certificate trust (`x5c`)
[source,json]
----
{
  "type": "x5c",
  "anchors": ["<base64-encoded-x509-certificate>"]
}
----

Validates the credential issuer against one or more X.509 trust anchors. The anchor is the Base64-encoded DER certificate.

.EUDI PID trust list (`eudi_pid_trust_list`)
[source,json]
----
{
  "type": "eudi_pid_trust_list",
  "trustListUrl": "https://example.com/trust-list.jwt",
  "trustListSigningCertificate": "<base64-DER-certificate>",
  "serviceType": "http://uri.etsi.org/19602/SvcType/PID/Issuance"
}
----

Validates the credential issuer against a EUDI trust list. The `trustListSigningCertificate` anchors the trust-list JWT signature, and `serviceType` filters entries by service type.

==== Binding rules

Binding rules ensure that supporting credentials are bound to the primary credential or the authenticated user.
They are configured on supporting credentials only.

.Claim equals primary claim
[source,json]
----
{
  "type": "claim_equals_primary_claim",
  "credentialClaim": "username",
  "primaryCredentialClaim": "username"
}
----

Verifies that a claim in the supporting credential matches a claim in the primary credential.

.Claim equals user attribute
[source,json]
----
{
  "type": "claim_equals_user_attribute",
  "credentialClaim": "family_name",
  "userAttribute": "lastName"
}
----

Verifies that a claim in the supporting credential matches a Keycloak user attribute. Built-in attribute mappings: `given_name`/`firstName`, `family_name`/`lastName`, `username`/`preferred_username`. Any other value is looked up as a custom user attribute.

==== Credential groups

Credential groups allow the wallet to choose between alternative credential combinations.
This is useful when multiple credential types can satisfy the same authentication requirement.

[source,json]
----
{
  "id": "primary-identity",
  "required": true,
  "options": [
    ["national-id"],
    ["drivers-license"]
  ]
}
----

[cols="1,3"]
|===
|Field |Description

|`id`
|Unique identifier for the group.

|`required`
|Whether the group is required (default: `true`).

|`options`
|Array of alternative credential combinations. Each option is an array of credential IDs that must all be presented together.
|===

When credential groups are used, the profile may contain multiple primary credentials.
Exactly one credential group must select a primary credential, and that group must be required.

[[presentation-during-issuance]]
=== Presentation during issuance

Presentation during issuance allows {project_name} to request a credential presentation as part of an OID4VCI issuance flow.
In this mode, the user identity comes from the issuance session rather than from claims in the presented credential.

To configure a presentation-during-issuance profile, set `identitySource` to `session` on the primary credential.
Binding rules are mandatory for session-identity credentials so that the presented credential is verified against the authenticated user.

[source,json]
----
{
  "id": "issuance-step",
  "displayCta": { "en": "Presentation during issuance" },
  "enabledForClients": ["test-app"],
  "credentials": [
    {
      "id": "pid",
      "role": "primary",
      "identitySource": "session",
      "format": "mso_mdoc",
      "credentialTypes": ["eu.europa.ec.eudi.pid.1"],
      "claims": ["eu.europa.ec.eudi.pid.1/given_name", "eu.europa.ec.eudi.pid.1/family_name"],
      "binding": [
        {
          "type": "claim_equals_user_attribute",
          "credentialClaim": "eu.europa.ec.eudi.pid.1/family_name",
          "userAttribute": "lastName"
        }
      ]
    }
  ]
}
----

Session-identity profiles are hidden from the login page and are only activated through internal OID4VCI flows.

=== Configuring the verifier policy for OpenID4VP authentication

Find the authentication flow dedicated to OpenID4VP authentication under authentication flows in the admin console.
The OpenID4VP authenticator in the flow is pre-configured with sensible defaults that can be adjusted to meet specific needs.

These settings include the accepted credential types, the maximum age of VP tokens presented, and related verifier-policy settings.
These policy settings are deployed through the authenticator configuration surface.

For the complete set of authenticator configuration properties, see xref:oid4vp-deployment-configuration.adoc[OpenID4VP deployment configuration reference].
