## Corrections to the previous attempt

1. **Postgres was not necessary.** The `fscert` image is built with
   `FEATURES="postgres,redis"`, but the runtime backend is a config choice: with
   `APP_DATABASE__BACKEND=memory` it starts and serves with no database. I ran the image
   standalone (no db) to confirm before changing the stack; the `status-list-db` service is gone.
2. **The JKS was not necessary.** The OID4VP plugin never reads a truststore file; it validates
   x5c chains through Keycloak's `TruststoreProvider` (`TrustAnchorAdapter`). One PEM entry is
   enough for both plugins.
3. **`KC_SPI_TRUSTSTORE_FILE_FILE` cannot take a PEM.** It is deprecated, detects the type from the
   file extension (`.jks`/`.p12`/`.pfx`, default `pkcs12`) and fails on PEM with
   "toDerInputStream rejects tag type 45". The supported form is `--truststore-paths=<file|dir>`,
   which does merge PEM. That is what the stack uses now.
4. **No generator script**, per review. The signing key is upstream's `test_data/certs/dev.key`,
   copied unchanged. One thing upstream cannot supply: its certificate is only valid for
   `DNS:localhost`, and the token-status plugin enforces hostname verification, so the stack
   reaches the server as `https://status-list:8443` and needs `status-list` in the SAN. The
   certificate is therefore self-signed from that same key for `DNS:localhost,DNS:status-list`; the
   exact `openssl req -x509` command is documented in
   `e2e/assets/crypto/status-list-server/README.md` (no script committed).

## Things that cost time (worth knowing)

- A `localhost:host-gateway` mapping is not reliable: here the container resolves `localhost` to
  `::1` first *and* `host-gateway` pointed at a stale `172.17.0.1`, so Keycloak kept getting
  `Connection refused` although the proxy was up. Using the compose service name avoids the whole
  class of problem.
- The realm URL is baked at render time (`assets/realm/index.ts` reads `STATUS_LIST_SERVER_URL`), so
  changing the default in `lib/config.ts` alone leaves the rendered realm stale — re-run
  `scripts/setup.sh` (or `pnpm clean`).
- `pnpm test` without the stack running fails with `ERR_CONNECTION_REFUSED` at `:14200`; use
  `pnpm play` (or `--keep-stack-alive`).
- Both a stray container on `:18092` and leftover `/tmp` compose projects broke early attempts;
  `docker compose down -v` in `e2e/` clears the stack.
